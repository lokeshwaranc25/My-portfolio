Troubleshooting

When something breaks at 2am

Most of my internship was support tickets — compute, storage, networking and access. Here's how I work a problem, and the failures I've actually chased down.

01

Reproduce it

Confirm the symptom myself before changing anything. Half of "it's down" turns out to be one browser or one stale DNS cache.

02

Find the layer

Work down the stack — DNS, load balancer, instance, application, database — until the failure stops following me.

03

Read the evidence

CloudWatch metrics and logs, ALB target health, EC2 status checks, CloudTrail for who changed what and when.

04

Fix the smallest thing

One change at a time, written down. If it needs a config change, it goes into Terraform rather than the console.

05

Make it loud next time

Add the alarm or dashboard panel that would have caught it, so the next occurrence pages us instead of a customer.

▲Compute and scaling

instance out of serviceCheck EC2 status checks and system logs first, then the target group health check path, port and timeout — a wrong health path fails far more often than a sick instance.
auto scaling not scalingVerify the CloudWatch alarm actually fires, the scaling policy is attached, and max capacity isn't already reached.
high CPU / memoryCorrelate CloudWatch metrics with deploy time, then look at the process rather than throwing a bigger instance at it.

◈Networking and connectivity

connection timed outSecurity group versus NACL — security groups are stateful, NACLs are not, so return traffic is the usual culprit. Then route tables, subnet and internet or NAT gateway.
dns not resolvingCheck the Route 53 record type and TTL, confirm with dig or nslookup, and watch for propagation rather than assuming a broken zone.
502 / 504 from the ALBUsually the target, not the balancer — check the app is listening on the registered port and the idle timeout isn't shorter than the response.

⚿Access and permissions

AccessDeniedRead the error — it names the action and the principal. Then the IAM policy simulator, the role's trust relationship, and any explicit deny or permission boundary above it.
assume role failedCheck the trust policy allows the caller, and that the session is using the role rather than the user's own keys.
s3 403 on a public siteBucket policy, Block Public Access, and object ownership all have to agree. Grant the minimum that works, not *.

▣Containers and Kubernetes

CrashLoopBackOffkubectl logs --previous for why the last run died, then describe for the events. Usually a missing env var, config map or failing readiness probe.
ImagePullBackOffWrong tag, wrong registry, or the node role lacks pull permission on the repository.
pod stuck PendingNo node has room — check resource requests against node capacity before blaming the scheduler.

⟳Pipelines and deploys

build fails only in CICompare the agent's runtime, versions and environment with local. Pin them so the pipeline stops being a different machine.
credentials not foundCheck the secret is scoped to the right branch or environment, and that it isn't expired or rotated out.
bad release shippedhelm rollback to the last good revision first, investigate second. Restore service, then find the cause.

◴Storage and data

disk full on the instanceUsually logs that were never rotated. Clear, then fix the rotation so it doesn't come back next month.
rds connections exhaustedCheck the connection pool on the application side before raising the limit on the database.
stale content servedCloudFront is still holding the old object — invalidate the path and set cache headers that match how often the file actually changes.
